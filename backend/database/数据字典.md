# 数据字典（字段中文名对照）

> 从 `travel_server` 库自动导出，与 `schema.sql` 完全同步；
> 改了表结构重新执行建表脚本后，再导出一次即可。

> 金额字段单位统一为「元」。

## config_log —— 配置调整留痕表：差标与部门预算的每一次增删改都记一条，只追加不修改

| 序号 | 字段名 | 类型 | 可空 | 默认值 | 键 | 说明 |
|:--:|---|---|:--:|---|---|---|
| 1 | `id` | bigint | 否 | - | 主键自增 | 留痕主键 ID |
| 2 | `item_type` | varchar(20) | 否 | - | 索引 | 变更类型：STANDARD 差标 / BUDGET 部门预算（部门的新增与删除也归在 BUDGET 维度） |
| 3 | `item_key` | varchar(64) | 否 | - | 索引 | 变更项标识：差标为「城市等级-交通方式」如 `二级-高铁`，部门为 `dept:3` |
| 4 | `action` | varchar(10) | 否 | - | - | 操作类型：INSERT 新增 / UPDATE 修改 / DELETE 删除 |
| 5 | `before_value` | varchar(200) | 是 | NULL | - | 调整前的值（字符串形式），新增时为 NULL |
| 6 | `after_value` | varchar(200) | 是 | NULL | - | 调整后的值，删除时为 NULL |
| 7 | `operator_id` | bigint | 否 | - | - | 操作人，关联 sys_user.id |
| 8 | `operate_at` | datetime | 否 | CURRENT_TIMESTAMP | 索引 | 操作时间 |
| 9 | `reason` | varchar(200) | 是 | NULL | - | 调整原因，管理层在 H-02 / H-03 页面上填写的原话 |

> 建表原因：`dept` 表只有一个 `monthly_budget` 字段，改完前值就丢了；`trip_standard` 虽然按版本存，
> 却没地方记「谁改的、为什么改」。H-04 的留痕原先是从版本链临时推导的，预算那半边查不出来，
> 管理层填的原因也只存在返回体里落地不了。这张表把三种动作统一收口，页面只读。

| 2 | `month` | char(7) | 否 | - | 唯一键 | 所属月份 `yyyy-MM`，一个月一条 |
| 3 | `input_hash` | varchar(128) | 否 | - | - | 生成时的入参指纹（场景 + prompt 版本 + 入参 JSON 的 sha256）；与当前指纹不一致即表示数据已更新 |
| 4 | `summary` | varchar(500) | 是 | NULL | - | 一句话总结 |
| 5 | `highlights_json` | text | 是 | NULL | - | 分级要点，形状同 `AiPointVO[]` |
| 6 | `drivers_json` | text | 是 | NULL | - | 归因分解，形状同 `MonthlyInsightVO.DriverVO[]` |
| 7 | `ratio` | decimal(12,4) | 是 | NULL | - | 快照当时的费效比 |
| 8 | `prev_ratio` | decimal(12,4) | 是 | NULL | - | 快照当时的上月费效比 |
| 9 | `delta` | decimal(12,4) | 是 | NULL | - | 快照当时的费效比环比变化，正数表示变差 |
| 10 | `prev_month` | char(7) | 是 | NULL | - | 对比的上一个月 |
| 11 | `sample_note` | varchar(300) | 是 | NULL | - | 快照当时的可信度说明（样本不足 / 回填率低 / 基准月不足） |
| 12 | `local_flag` | tinyint | 是 | 1 | - | 1 = 规则生成的本地版本，0 = 真走了模型 |
| 13 | `model` | varchar(40) | 是 | NULL | - | 实际模型名 |
| 14 | `prompt_version` | varchar(20) | 是 | NULL | - | 生成时的 prompt 版本号，升版即视为指纹变化 |
| 15 | `generated_at` | datetime | 否 | CURRENT_TIMESTAMP | 索引 | 报告生成时间，页面上「更新于」读这个 |
| 16 | `generated_by` | varchar(20) | 否 | AUTO | - | 生成方式：AUTO 首次读取 / SCHEDULED 凌晨定时 / MANUAL 手动重新分析 |

> 建表原因：`ai_log` 记的是「每一次模型调用」，本表存的是「这个月当前生效的那份报告」，
> 两者互补而不重复。月报页读一次报告不应该石墨烧一次模型调用，也不该每次打开看到的都不一样；
> 反过来，管理层要看得出来这份解读是哪一天、基于什么样的数据出的 —— `generated_at` 与
> `input_hash` 就是为此存在的。
>
> 更新规则：当月每天凌晨 0 点自动重出（`travel.ai.insight-cron`，服务半夜没开机会在启动时补跑）；
> 已过完的月份只在每月 1 号结算一次；事后补录让数据变了，页面会以「数据已更新」标签提示，
> 由人决定要不要点「重新分析」。

## field_draft —— 理由字段草稿表：五处理由输入框的暂存，只保留最后一次

| 序号 | 字段名 | 类型 | 可空 | 默认值 | 键 | 说明 |
|:--:|---|---|:--:|---|---|---|
| 1 | `id` | bigint | 否 | - | 主键自增 | 草稿主键 ID |
| 2 | `biz_type` | varchar(20) | 否 | - | 唯一键 | 业务场景：APPLY_REVIEW 审批意见 / EXPENSE_REVIEW 财务复核说明 / EXPENSE_PAY 付款备注 / EXPENSE_SUBMIT 强制提交说明 / APPLY_SUBMIT 超标说明 |
| 3 | `biz_no` | varchar(32) | 否 | - | 唯一键 | 业务单号：APPLY_* 记申请号，EXPENSE_* 记报销单号 |
| 4 | `field_name` | varchar(32) | 否 | - | 唯一键 | 字段名，与前端表单字段名一致：opinion / reviewReason / payRemark / forceReason / exceedReason |
| 5 | `user_id` | bigint | 否 | - | 唯一键、索引 | 草稿归属人，关联 `sys_user.id`；只认本人的草稿 |
| 6 | `content` | varchar(200) | 否 | - | - | 草稿正文；清空即删行，不留空内容占位 |
| 7 | `updated_at` | datetime | 否 | CURRENT_TIMESTAMP | 索引 | 最后一次保存时间，页面上「已保存 · 10:42」读这个 |

> 建表原因：审批意见、复核说明、付款备注、强制提交说明、超标说明这五处
> 都是「一句话要斟酌很久」的文本框，写一半丢了的代价很高，而它们所在的单据
> 此时已有确定的业务状态（待审批 / 待复核 / 待付款），没有「整单存草稿」这一档可挂。
> 五处形状完全一样（某人 + 某张单 + 某个字段 = 一段文字），
> 差别只在 `biz_type` 与 `field_name`，因此用四元组唯一键而不是铺五张表。
>
> 与业务表的关系：草稿只暂存，正式值仍写在业务表上
> （`approval_record.opinion` / `payment_record.pay_remark` /
> `expense_report.force_reason` / `expense_report.review_reason` / `trip_apply.exceed_reason`）。
> 提交成功那一刻草稿失效，由 Service 层顺手清掉。
> 它不参与任何计算、统计与留痕——不是业务事实，只是输入框的一份暂存。

## ai_correction —— 人工修正留痕表：系统给的值被人改成了什么，只追加不修改

记「系统给了一个值，人改成了另一个值」。与 `ai_log` 的分工：`ai_log` 说模型这一次跑得怎么样，
这张表说人认不认这个值。采纳率只说「有没有被采用」，这张表才指向该改哪句 prompt。

两个采集点：票据 OCR 回填后员工手改（`scene = OCR_INVOICE`）、填写助手的建议值 vs 最终提交值（`scene = APPLY_ASSIST`）。

| # | 字段 | 类型 | 可空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|---|
| 1 | `id` | bigint | 否 | 自增 | 主键 | 留痕主键 ID |
| 2 | `scene` | varchar(30) | 否 | - | - | 来源场景：`OCR_INVOICE` 票据识别回填 / `APPLY_ASSIST` 填写助手建议 |
| 3 | `biz_type` | varchar(20) | 是 | NULL | 索引 | 单据类型：`INVOICE` / `TRIP_APPLY`；还没落库的新建单留空 |
| 4 | `biz_no` | varchar(64) | 是 | NULL | 索引 | 票据存发票号，申请单存申请号（新建单用 NEW + 用户 id） |
| 5 | `field_name` | varchar(40) | 否 | - | 索引 | 被改的字段名：`invoiceNo` / `amount` / `invoiceDate` / `seller` / `reason` / `tripType` |
| 6 | `old_value` | varchar(255) | 是 | NULL | - | 系统给的值（OCR 识别值 / AI 建议值） |
| 7 | `new_value` | varchar(255) | 是 | NULL | - | 人最终填进去的值 |
| 8 | `operator_id` | bigint | 是 | NULL | - | 修改人，关联 sys_user.id |
| 9 | `created_at` | datetime | 否 | CURRENT_TIMESTAMP | 索引 | 修改时间 |

> 两个值一律用文本存：票号是数字串、金额是小数、日期是文本，统一成文本才不用为每种类型开一列
> （金额比对时按数值比，先抹掉尾零与千分位）。只有实质不同才写一行——识别的 1560.00 与人填的 1560 是一回事。

## apply_remind —— 申请单催办记录表：申请人催一次写一行，只追加不修改

催办不改任何单据状态，所以必须单独记：`approval_record` 记的是审批人做了什么，这里记的是申请人等不及了。
不进 `config_log`——那是配置变更（差标、预算）的留痕，把催办塞进去会让那本账混进业务动作。
催办节流（同一人同一单 24 小时一次）就落在这张表上：以库里的行为准，重启也一样。

| # | 字段 | 类型 | 可空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|---|
| 1 | `id` | bigint | 否 | 自增 | 主键 | 催办主键 ID |
| 2 | `apply_no` | varchar(32) | 否 | - | 索引 | 被催的申请单号 |
| 3 | `step` | varchar(20) | 是 | NULL | - | 催办时单据所处的环节：`DEPT_REVIEW` / `FINAL_REVIEW` |
| 4 | `from_user_id` | bigint | 是 | NULL | - | 谁催的，关联 sys_user.id |
| 5 | `note` | varchar(200) | 是 | NULL | - | 催办时留的一句话 |
| 6 | `remind_at` | datetime | 否 | CURRENT_TIMESTAMP | 索引 | 催办时间 |
